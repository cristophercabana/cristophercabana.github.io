Minecraft Mod Reversing #1 - Hook Conflict (Kamui Bug)

I am documenting practical reverse engineering cases, including real-world debugging scenarios in modded environments.

Scenario

A friend was running a Naruto-based Minecraft server using a modpack. One of the core abilities, Kamui (intangibility), was not working correctly.

The issue was:

After activating Kamui once, the player remained permanently intangible.

Initial Analysis

The first step was to inspect the original mod:

Target: narutomod.jar

Using Recaf, I analyzed the bytecode and logic related to the variable:

kamui_intangible

The behavior was correct:

  • The value was properly toggled
  • Cooldown logic was implemented
  • No obvious bug was present

This indicated that the issue was not in the original mod.

Expanding the Scope

Since this was a modpack, the issue could be caused by another mod.

Further analysis revealed the presence of a hooking system.

Hook Identification

A second mod contained the following structure:

@Hook(returnCondition = ReturnCondition.ALWAYS, at = @At(point = InjectionPoint.HEAD))

This means:

  • The hook executes at the beginning of the method
  • ReturnCondition.ALWAYS forces the original method to never execute

Effectively, the original Kamui logic was being completely replaced.

Root Cause

The bug was not a flaw in the original implementation, but a conflict between mods.

The hook modified the behavior of Kamui and failed to correctly reset the state, causing permanent intangibility.

Fix

The responsible code was located inside:

The_Shinobi_Way_V1.2.jar

Using Recaf, the hook was identified and removed by deleting the injection logic.

This restored the original execution flow.

Result

  • Kamui intangibility works as intended
  • State resets correctly after use
  • No more permanent invulnerability

Key Takeaways

  • In modded environments, behavior can be overridden externally
  • Hooks can completely replace original logic
  • Reverse engineering is essential to trace real execution flow

Notes

This case demonstrates a real-world application of reverse engineering beyond CTF challenges, involving bytecode analysis, mod interaction, and runtime behavior modification.
